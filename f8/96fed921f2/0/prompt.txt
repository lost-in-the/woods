### 1. Incremental mechanics & cost (`extract_changed`, `extractor.rb:289–326`)
**Inputs it needs:**
- A prior **`dependency_graph.json`** in the output dir (`extractor.rb:291–292`). It's loaded via `DependencyGraph.from_h`. **No prior graph → empty graph → `affected_by` returns nothing → zero units re-extracted.** The graph is mandatory, not optional.

No stored SHA of its own — it derives the diff from env/git each run. Files are filtered to a relevant-path allowlist (`woods.rake:76–98`: models, controllers, services, jobs, migrations, `schema.rb`, `routes.rb`, `Gemfile.lock`, etc.).

**What it re-extracts:** directly-changed units **+ their transitive dependents** (BFS over reverse edges, unbounded depth — `dependency_graph.rb:65–86`). Each affected unit is re-run through its extractor and rewritten; affected type `_index.json`s regenerated.

**Rails boot still required — YES.** `extract_changed` calls `safe_eager_load!` (`extractor.rb:297`) exactly like full extraction. The boot + `eager_load!` is a fixed floor both modes pay.

**Cost vs full:** The **Rails boot + eager-load dominates** for a large app and is *identical* in both modes. Incremental only saves the extractor-scan pass + git enrichment (`git log` over all files). So on a ~6,500-unit app incremental saves extraction *minutes*, not the boot. This matches ENG-5480's own framing ("saves extraction time, not API calls").

**⚠️ Two correctness caveats I confirmed:**
- **Incremental misses newly-added files.** `affected_by` seeds from `@file_map[f]` (`dependency_graph.rb:66`); a file not already in the (main) graph isn't found, so a PR that *adds* a model/service is silently not extracted. Same for renames (old identifier lingers, new one absent).
- **`extract_changed` skips `resolve_dependents` and `write_graph_analysis`** (both only run in `extract_all`, lines 246/270). It *does* recompute PageRank at write time (`:724`), but **`graph_analysis.json` goes stale** after an incremental run (hubs/orphans/cycles not refreshed).

### 2. Recommended freshness strategy — **the latest `main` graph is good enough; do NOT re-index the PR branch**
The reviewer's core question is *"what depends on the changed units"* — i.e. **reverse-dependents + PageRank**. Those reverse edges are a whole-codebase property that lives almost entirely in `main` and is highly stable (e.g. `Account` = 340 dependents / PageRank #1). A PR changes a unit's *forward* deps, not the set of things that depend on it. **So map the PR's changed files → units (via `file_map`) → reverse-dependents + PageRank from the restored main graph.**

**When a stale main graph misleads (call these out in the report, don't re-index for them):**
- PR **adds** a unit → absent from main's graph (no node, no `file_map` entry).
- PR **renames/moves** a unit → old identifier's dependents shown, new one missing.
- PR **deletes** a depended-on unit → dependents still listed (that's actually the useful signal: "you're removing something 40 things depend on").
- New **forward** edge added by the PR (changed file now calls X) → not in main graph, but this is secondary for blast-radius.

### 3. Recommended iterative-push handling (PR pushed 10×/day) — **stable main graph + per-push file-diff; never re-extract per push**
Re-extraction (full *or* incremental) pays a Rails boot every push — far too expensive for 10 pushes. Instead:
- **Restore the last main `dependency_graph.json` once** (ENG-5462/5480 restore plumbing) and treat it as read-only.
- **Per push, only recompute the changed-file list** and re-run the (cheap, no-boot, deterministic) file→unit→reverse-dependents+pagerank query.
- **Debounce:** trigger on a settled push (Buildkite `concurrency_group` + cancel-superseded so push #7 doesn't post while #8 is in flight).
- **Comment idempotency:** maintain **one sticky PR comment** (find-and-update by a hidden marker via `gh`), not 10 new ones. Optionally diff against the last posted blast-radius and only re-post/flag when the changed-unit set actually changes — most pushes touch the same files.

Cost tradeoff: this is ~seconds of graph lookup per push vs minutes of boot+extract. The only thing you lose by not re-indexing is picking up brand-new units the PR adds — acceptable, and detectable (a changed file with no `file_map` hit → flag "new unit, no blast-radius data yet").
