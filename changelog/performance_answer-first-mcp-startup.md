- The Index MCP server answers `initialize` before it warms its caches (WDS-78). The reader warm-up and the lexical corpus build run on one background thread that starts once the handshake response is on the wire, so the handshake takes under a second on any index size instead of 9-13 s on ~11,000 units, inside the 5 s probe after which Claude Code records the server as rejecting `initialize` and connects only on a later pass. A tool call that arrives during the warm-up waits for it (`WOODS_MCP_HYDRATION_WAIT_SECONDS`, default 30) and then answers from the warmed caches; after a failed warm-up it answers from the cold reader. Past the cap it waits on nothing the warm-up holds: reader-backed tools answer from the cold reader, and lexical `codebase_retrieve`, whose corpus is what the warm-up is building, answers a non-error, retryable `warming` result with no sources (`structuredContent.data.status: warming`, `retryable`, `retry_after_seconds`); never an error or a partial result. A `reload` or a newly published generation during the warm-up does not queue every other call behind it: the warm-up yields its generation pins and restarts on the new generation. `woods_status` reports the warm-up under `hydration` (`state`: `warming`, `ready` or `failed` with the error, plus `warmup`, `started_at`, `finished_at` and `duration_seconds`); `bootstrap` is unchanged. A warm-up exception is captured into `hydration.state: failed` and the server keeps serving. The self-map server benefits on every launch that finds a built map; a first launch still builds the map before the server starts.
