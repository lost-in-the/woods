- `woods:embed` and `woods:embed_incremental` write each batch's metadata records inside one metadata-store transaction. On SQLite that is one journal commit per batch (32 records by default) instead of one autocommit per record, which was the fsync-per-row cost behind slow incremental runs; and a batch whose embedding fails after its records were stored now rolls those records back instead of leaving partial rows. Metadata stores gain `#transaction`: the SQLite adapter wraps the block in BEGIN/COMMIT (joining an open transaction), the in-memory adapter and the Interface default simply yield. The transaction spans the whole batch, provider call included, so the SQLite write lock is held for the batch's duration: the indexer is the store's only writer and pipeline runs serialise on the pipeline lock, and in SQLite's rollback-journal mode an open write transaction does not block readers such as the Index Server's retrieval, only the commit itself does, within `busy_timeout`.
