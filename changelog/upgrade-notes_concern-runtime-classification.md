- A module is now a `concern` unit when it extends `ActiveSupport::Concern`, wherever it lives, as well as when it lives in a concerns directory (#996). Woods checks the loaded module by name (`singleton_class.include?(ActiveSupport::Concern)`), so `extend ::ActiveSupport::Concern` counts and a comment or string that mentions it does not. **Some `poro` and `lib` units become `concern` units:** a module outside `app/**/concerns` that extends `ActiveSupport::Concern` moves from `poros/` (or `libs/`) to `concerns/`, and its typed identity changes from `poro:` (or `lib:`) to `concern:`; its identifier is unchanged. Such a module is published once, as a concern, even when nothing includes it, and `inlined_concerns` entries and `include` edges that name it now resolve to that concern unit. PORO module units no longer carry `metadata.active_support_concern`. On concern units, `metadata.concern_type` and `uses_active_support` now follow the loaded module itself rather than any `extend ActiveSupport::Concern` text in its file. A file under a concerns directory whose hook or method names appear only in comments is no longer a concern unit. **Limit:** a module that is never loaded (for example a `lib/` file outside the autoload paths) has no runtime answer and keeps its current type; that is not a claim about what it is. Run `woods:extract` once after upgrading; an incremental run moves only the modules it re-reads.
