## 1. Chunking: a verified documentation/implementation mismatch

**Source inspection and local reproduction.** The response lists `summary`,
`associations`, `callbacks`, `validations`, `scopes`, and `methods` as model
extractor chunks. That list appears verbatim in Woods' extractor reference, but
does not match `ModelExtractor#build_chunks` at the pinned commit.

The implementation builds these kinds, with conditional emission:

```text
summary
associations
callbacks
callback_effects
validations
```

These are metadata-derived text summaries. In particular:

- The summary lists column names, counts, and up to ten instance-method names;
  it does not supply those methods' bodies.
- The callback chunk gives the event grouping, filter names, and selected detected
  effects. Its formatter does not include the callback's `conditions`.
- The validation chunk gives attributes and validator types. It does not include
  validator options or conditional predicates.
- This builder does not emit dedicated `scopes` or `methods` chunks.

Sources: [model chunk builder][W1], [callback formatter][W2],
[validation formatter][W3], [the conflicting documentation][W4].

There is a **separate source-based `Woods::Chunking::ModelChunker`** that can emit
scope and method source sections. I invoked it locally and confirmed that
distinction. However, it is marked `@api private`, and its existence does not mean
those source sections are present in `PublishedIndex#unit(...)["chunks"]`.
The embedding indexer's inspected path invokes its source chunker only when the
unit's chunks are empty and chunking is needed; pre-existing chunks instead go
through size-limit enforcement. [Source chunker][W5], [indexer selection][W6].

### Concrete reproduction

I supplied two synthetic model units to the actual current model chunk builder.
Both had a callback named `normalize_email`, the same schema metadata and
registrations, and side-effect annotations generated by `CallbackAnalyzer` from
their respective source. The callback bodies differed:

```ruby
# Variant A
def normalize_email
  self.email = email.downcase
end

# Variant B
def normalize_email
  self.email = email.upcase
end
```

**Their entire emitted chunk arrays were identical**, including content hashes.
Their callback chunks were both:

```text
# SampleRecord - Callbacks

before_save:
  normalize_email [writes: email]
```

Changing the callback metadata from `if: normalization_needed?` to
`unless: normalization_needed?` also left the emitted chunks identical.
The separately invoked source chunker retained the method body and produced a
`methods` section. These probes ran the chunk-building components without booting
Rails; they do not establish full application behavior or Jev accuracy.

For a hypothetical requirement that saved email be lowercase, the first pair's
distinguishing evidence has been lost from the summary chunks. A model receiving
only those identical chunks cannot distinguish the implementations from them.
**If the actual request also contains the relevant diff or source, that evidence
can restore the distinction.** This probe is not proof that the proposed adapter
already has a defect; it identifies the assumption to check in its real payload.

### Suggested adjustment

Use chunks as useful selected context, but inspect their actual content and origin.
Do not substitute a callback summary for its implementation or conditional
metadata. A packet may need several related sections: the changed operation,
callback registration, helper body, policy, and relevant test.

For the first trial, selecting the required source from the pinned unit or physical
snapshot is sufficient. There is no need to finish a new chunking system first.
If source chunking is used, keep relationships visible in the same request when
the question requires comparing them. TypeSafe evaluates each request's state
independently; it does not automatically connect fragments sent in different
requests. [TypeSafe state contract][T1].

This is also a Woods documentation correction worth retaining for separate work:
describe the extractor's actual emitted chunks separately from the source chunker.
I have not opened an issue or changed that canonical document in this review.

## 2. One-hop resolution improves coverage, not completeness

**Design inference, supported by the inspected analyzer's bounded mechanism.**
If “trustworthy on its own” means clearer about what was inspected, I agree with
the suggested unresolved marker. If it means an empty annotation can establish
that no relevant effects occur, one-hop resolution does not provide that result.

For example:

```text
normalize -> dispatch_normalization -> set_status -> column write
```

Following one helper level still misses the next level. Correct method ownership
also matters: inheritance, prepended modules, overridden methods, `super`, and
dynamic dispatch are not solved by matching a method name in the source tree.
The current analyzer locates the first matching method definition in its supplied
AST; it is not a runtime dispatch resolver. [Method lookup implementation][W7].

A future extension could separately describe:

- whether the callback's actual implementation was located;
- which source bodies were analyzed;
- traversal depth and unresolved calls;
- the detected effects, without claiming these exhaust all behavior.

These are proposed semantics, not fields Woods currently promises. A resolved
method can still have partially analyzed behavior. An unresolved flag alone
cannot express all of that.

There is also a tension in “ship the callback method source alongside the
annotation”: if that method only calls a helper, its body alone still lacks the
helper's behavior. For the pilot, include the small relevant helper/source set or
report that the evidence is incomplete. Avoid making a new analyzer a prerequisite.

Adding fields is often a reasonable compatibility strategy, but it does not
remove the need for a public-contract review, consumer checks, specs, and matching
documentation. Woods' instructions explicitly treat generated artifacts as a
compatibility surface. That is a consideration for a separate Woods change,
not a blocker for using the existing evidence conservatively. [Repository policy][W8].

## 3. Clean CI simplifies verification; it does not replace it

**Contract inspection and counterexamples.** A clean checkout can coexist with:

- an index restored from a cache generated at an earlier revision;
- a checkout of the wrong target revision;
- a checkout of a merge result when the review packet describes the branch head;
- source-matching artifacts with an unverified boot/consumption boundary.

Thus freshness and revision identity do not collapse merely because Git reports
no working-tree changes. A controlled CI job can establish both together if it
checks the intended revision, builds or verifies the index against that snapshot,
and keeps the packet's before/after and source selection consistent.

Keep the two ledger fields, even when both are satisfied by a simple CI sequence.
This need not become a complicated framework: record the actual checked-out
revision, the intended review revision/range, the pinned generation, and its
freshness result/reasons. Also preserve the third field, per-check evidence
sufficiency. [Source-freshness contract][W9].

## 4. Smaller clarification: Nouls still support decision bands

The correction about the missing `confidence` field is sound. It should not become
“Nouls cannot express uncertainty or support routing.” Their value is the
probability of yes: near zero is a strong no, near one a strong yes, and near the
middle the alternatives have similar probability. [Noul reference][T2].

An application can use an explicitly evaluated probability policy for clear
positive, clear negative, and unresolved answers. Keep that separate from whether
the required evidence was supplied. Missing known prerequisites should remain
unassessed regardless of how extreme a returned probability is. Conversely, file
presence in the ledger does not prove semantic sufficiency or answer correctness.

No additional model call is required just to implement these distinctions. If a
later design adds a question about evidence sufficiency, its answer is another
judgment to test, not a substitute for provenance checks.

## Bias and limits of this review

The author's chunking claim was supported by a misleading Woods documentation
line; treating it simply as careless verification would be unfair. My previous
review also missed the distinction between those two chunking paths. The local
probe resolves that specific disagreement; it does not establish that compact
packets are generally worse than full units.

Likewise, the CI statement may have been shorthand for a pipeline that already
checks the revision and performs fresh extraction. Verify that implementation
before calling it broken. The one-hop proposal may have intended bounded,
better-labeled evidence rather than exhaustive analysis; make that scope explicit.

Our shared expectation that another prose review has diminishing value is
reasonable, but “nothing else could be found” was too strong: the chunk mismatch
is consequential. It is a reason for one small payload check, not indefinite
planning. This review contains no Jev inference and cannot decide the bank's
effectiveness in either direction.
